# قوانین

قبل از هر تغییر این فایل را بخوان.

## کامنت

### کامنت فایل

بالای هر فایل `.c` / `.h`:
- لحن مهندسی، نه آموزشی
- انگلیسی و فارسی اجباری

### کامنت تابع

بالای هر تابع:
- کار تابع چیست (انگلیسی و فارسی)
- هر پارامتر یعنی چی، واحدش چیست، محدوده‌اش چیست (مثلاً mV، ms، درصد)
- مقدار برگشتی چیست
- مثال: `@param u32_batteryMv [EN] Battery voltage in mV, 21V=0% 28V=100% / ولتاژ باتری`

## هماهنگی

قبل از **هر** تغییر (کد، README، AI، پوشه):
1. بگو کدام فایل‌ها عوض می‌شوند
2. بگو چرا
3. صبر کن تا کاربر تأیید کند
4. بعد انجام بده

بدون تأیید، فایل را عوض نکن.

## خوانایی و ساختار کد

### سادگی و خوانایی توابع

توابع را ساده و خوانا بنویس تا بشه بعدا اصلاحشون کرد — صرفاً خطی ننویس چون از خوانایی می‌اندازد.
- هر تابع یک کار کند (Single Responsibility)
- از ifهای تودرتوی عمیق پرهیز کن، ولی گام‌ها را با نام متغیر واضح و کامنت جدا کن تا خوانا بماند، نه فقط پشت‌سرهم on/delay/off
- تابع بازر جدا باشد و از هر سناریو قابل صدا زدن باشد
- بالای هر تابع حتماً توضیح بده چیکار می‌کنه و هر پارامتر یعنی چی (واحد، محدوده)

### فرمول‌ها خطی نباشد

فرمول‌ها را خطی ننویس — فرمول خطی خوانایی را از بین می‌برد.

- هر فرمول را به گام‌های کوچک با متغیرهای معنادار خورد کن، نه یک خط طولانی
- مثال بد (خطی):

```c
uint8_t__pct = (uint8_t)((offset * 100u) / range);
```

- مثال خوب (غیرخطی، خوانا):

```c
uint32_t uint32_t__voltageRangeMv = UI_BAT_V_MAX_MV - UI_BAT_V_MIN_MV;
uint32_t uint32_t__voltageOffsetMv = batteryMv - UI_BAT_V_MIN_MV;
uint32_t uint32_t__scaledOffset = uint32_t__voltageOffsetMv * 100u;
uint8_t uint8_t__batteryPercent = (uint8_t)(uint32_t__scaledOffset / uint32_t__voltageRangeMv);
```

- برای چشمک: اول درصد باقی‌مانده، بعد دوره تقسیم بر ۱۰۰، بعد ضرب، بعد کف، بعد محاسبه on/off — هر گام یک متغیر با نام مرتبط
- این قانون برای همه فرمول‌ها (باتری به درصد، چشمک زرد، سبز، محاسبه بوق) اجباری است

### جداسازی توابع و بخش‌ها

#### علامت جداکننده

کل توابع را با علامت مشخص از هم جدا کن که اول و آخرشان مشخص باشد.

- از جداکننده‌های یکسان استفاده کن: `/* ==================== Buzzer / Beep ==================== */`
- هر گروه تابع یا هر تابع با این علامت از بقیه جدا شود تا اسکرول سریع و خوانایی بالا برود
- در همه فایل‌های `.c` و `.h` این قانون رعایت شود (حداقل برای هر بخش)

#### جداسازی بازر از LED

بازر را از LED در کد جدا کن (LED اول، بازر آخر).

- ساختار اجباری `ui.c`:

```c
/* ==================== Includes ==================== */
/* ==================== LED Low-Level ==================== */  // green, red, yellow, all_off
/* ==================== LED Scenarios ==================== */ // InputOk, BatteryRun, Charging, Tick
/* ==================== Buzzer / Beep ==================== */ // buzzer low-level, calc_beep_on, pattern
```

- داخل هر بخش، توابع مربوط به همان کار باشد، نه قاطی
- این جداسازی تا آخر پروژه رعایت شود

## RTOS ساده و خوانا - بدون قفل میکرو

برنامه کاملاً به شکل RTOS نوشته شود ولی ساده و خوانا بماند، نه شلوغ.

- از `HAL_Delay` اصلاً استفاده نکن (میکرو را قفل می‌کند، همه تسک‌ها می‌ایستند)
- در RTOS از `vTaskDelay` یا `vTaskDelayUntil` استفاده کن — این‌ها میکرو را قفل نمی‌کنند، فقط همان تسک می‌خوابد و بقیه تسک‌ها (measurement, protection, control) اجرا می‌شوند
- پس `vTaskDelay` داخل تسک‌ها مجاز است و ساده و خواناست، ولی داخل توابع ماژول که منطق طولانی دارند، بهتر است خورد شود یا با `vTaskDelayUntil` دوره‌ای شود
- کارهای طولانی را خورد کن تا میکرو قفل نکند: هر تسک هر بار یک کار کوچک انجام دهد و با `vTaskDelay(10ms)` یا `vTaskDelayUntil` برگردد
- الگوی ساده RTOS و خوانا:

```c
void func__TaskUi(void *arg) {
  TickType_t lastWake = xTaskGetTickCount();
  for (;;) {
    vTaskDelayUntil(&lastWake, pdMS_TO_TICKS(10));
    func__Ui_Tick(inputMv, batteryMv); // یک تیکه کوچک، بدون delay داخلش
  }
}
```

یا اگر خواستی داخل سناریو delay داشته باشی، چون RTOS است و فقط همین تسک می‌خوابد، مجاز و خواناست:

```c
void func__Ui_ScenarioInputOk(void) {
  green(true); red(false); yellow(false);
  vTaskDelay(pdMS_TO_TICKS(500)); // فقط Ui می‌خوابد، بقیه تسک‌ها کار می‌کنند
}
```

- مهم: `HAL_Delay` ممنوع، `vTaskDelay` در تسک مجاز و ساده است. کد را شلوغ نکن با استیت‌ماشین‌های خیلی پیچیده اگر با یک `vTaskDelay` ساده هم میکرو قفل نمی‌شود
- تا آخر پروژه RTOS ساده و خوانا بماند، نه شلوغ

## نام‌گذاری

### قانون کلی `__` (دو آندرلاین)

در تمام نام‌گذاری‌ها (متغیر، تابع)، بعد از تایپ از **دو آندرلاین `__`** استفاده کن (بجای یکی) برای تفکیک بهتر و قابل تعریف بودن.

### متغیر

- اول تایپ کامل بعد نام متغیر: تایپ کامل مثل `uint8_t`, `uint16_t`, `uint32_t`, `int32_t`, `bool`, `float`
- بعد از تایپ `__`: مثلاً `uint32_t__inputVoltageMv`
- اگر گلوبال بود تایپ با حروف بزرگ و با `__G__`: مثلاً `UINT32_T__G__InputVoltageMv`, `UINT8_T__G__BatteryPercent`, `BOOL__G__InputPresent`
- اگر داخلی (لوکال) بود تایپ با حروف کوچک و `__`: مثلاً `uint32_t__inputVoltageMv`, `uint8_t__batteryPercent`, `bool__inputPresent`
- برای استاتیک سطح فایل هم قانون گلوبال (حروف بزرگ) اعمال می‌شود: `UINT32_T__G__UiBatteryRunBeepCycleCnt`
- **نام باید مرتبط با کاری باشد که برایش نوشته شده**: نام متغیر باید بگوید چه کاری می‌کند، نه نام عمومی مثل `tmp`, `data`, `val`
  - خوب: `uint32_t__batteryVoltageMv`, `uint8_t__batteryPercent`, `bool__inputPresent`, `uint32_t__greenBlinkOnMs`, `uint32_t__buzzerTotalOnMs`
  - بد: `uint32_t__x`, `uint32_t__temp`, `uint8_t__val`

### ثابت (`#define`)

- هر ثابت `#define` باید با نام ماژول/فایل شروع شود تا معلوم باشد کجا تعریف شده
- مثال: `UI_SELFTEST_LED_MS` یعنی ثابت ماژول UI، در فایل `ui.h` (single source برای UI) تعریف شده
- **آیا `UI.c_UI_SELFTEST_LED_MS` شدنی است؟**
  - در C نام ماکرو فقط حروف، عدد و `_` می‌تواند داشته باشد، نقطه `.` غیرمجاز است، پس `UI.c_...` کامپایل نمی‌شود
  - اگر بخواهی نام فایل را دقیق بیاوری باید با `_` بنویسی: `UI_CONFIG_SELFTEST_LED_MS` یا `UI_C_SELFTEST_LED_MS`
  - ولی `UI_` خودش همین کار را می‌کند: `UI_` یعنی ماژول UI، و چون همه ثابت‌های UI در یک فایل واحد `ui.h` هستند، `UI_` عملاً نام فایل/ماژول را نشان می‌دهد
  - برای ماژول‌های دیگر: `TASK_STACK_UI`, `TASK_PRIO_UI` در `rtos_config.h` هستند (پیشوند `TASK_` + نام ماژول)، `PIN_LED_G_PORT` در `board_pins.h` (پیشوند `PIN_`)
  - پس قانون فعلی: ثابت‌ها با پیشوند ماژول شروع شوند (`UI_`, `TASK_`, `PIN_`, `MODULE_`, `APP_`) که خودش نام فایل/ماژول را می‌رساند
- همه ثابت‌های جدید باید همین قانون را رعایت کنند و مرتبط با کارشان نام‌گذاری شوند

### تابع

- فقط توابعی که خودمان می‌نویسیم (Firmware/App, Bsp, Modules, Rtos, Config) باید اولشان کلمه `func__` با **دو آندرلاین `__`** اضافه شود (بجای یکی)
- به توابع سیستمی (HAL, FreeRTOS, CMSIS) کاری نداشته باش
- مثال: `func__Ui_Init`, `func__Ui_BoardTest`, `func__Ui_BuzzerPatternMs`, `func__BspGpio_Write`, `func__App_Start`, `func__TaskUi`
- برای `static` داخلی هم همین قانون: `func__green`, `func__all_off`, `func__calc_beep_on`
- در `.h` و `.c` و جاهایی که صدا زده می‌شود همه باید با `func__` بیاید
- **نام فایل اولش نیاید**، فقط بعد از تایپ `__` باشد (مثلاً `uint32_t__` و `func__`)

### محل تعریف ثابت‌های UI

فایل `ui_config.h` حذف شد. همه ثابت‌های قابل تنظیم UI (Vmin/Vmax, Vth, blink, beep, buzzer pattern) در همان `ui.h` هستند (single source در خود ماژول). `task_ui.c` و `app_config.c` هم از `ui.h` می‌خوانند. اگر ثابت جدید UI اضافه شد، فقط در `ui.h` بگذار.

## مدیریت حافظه

مدیریت حافظه را در تمام کارها در نظر داشته باش تا آخر پروژه هم این کار را باید انجام بدی.

- در `Firmware/` از `malloc/free` استفاده نکن؛ فقط تخصیص استاتیک
  - تسک‌ها با `xTaskCreateStatic` ساخته شوند (نه `xTaskCreate` که malloc می‌کند)
  - بافرهای Idle/Timer در `freertos_hooks.c` استاتیک باشند (`s_idle_tcb`, `s_idle_stack`)
  - `heap_4.c` هست ولی استفاده نشود؛ اگر شد، دلیل بنویس
- اندازه استک تسک‌ها در `rtos_config.h` با واحد **word** (نه بایت) تعریف شود و در `README` هر ماژول ذکر شود
- از آرایه‌های بزرگ روی استک پرهیز کن؛ اگر لازم بود `static` یا `const` بگذار یا سایز را در `rtos_config.h` زیاد کن
- `APP_CONFIG` و همه جدول‌های ثابت باید `const` باشند تا در Flash بمانند نه RAM
- `vApplicationStackOverflowHook` باید فعال باشد و در سرریز، اینتراپت‌ها را خاموش و در حلقه بی‌نهایت بماند
- بعد از هر اضافه کردن پریفرال یا ماژول، RAM/Flash مصرفی را چک کن (Map file) و در README بنویس
- تا آخر پروژه، هر تغییر باید از نظر حافظه بررسی شود (استک، هیپ، بافر DMA، تعداد تسک)

### برگه هر ماژول

ریشهٔ `Firmware` برگهٔ README جدا ندارد. فقط همین فایل AI.

هر ماژول یک `README.md` داخل **همان پوشه** دارد. راهنمای ماژول دیگر ساخته نشود.

هر بار همان ماژول عوض شد، همان جلسه یک خط در بخش **تاریخچه** همان README اضافه کن.

قالب اجباری `README.md` ماژول:

1. **وضعیت** — فعال یا اسکلت؛ مقدار `MODULE_*` در `modules_enable.h`
2. **تاریخچه** — تاریخ + چه عوض شد (از جدید به قدیم)
3. **فایل‌ها** — `.c` / `.h` همین پوشه و تسک مربوط در `Rtos`
4. **توابع** — نام دقیق + کار (عمومی، `static` داخلی، تسک)
5. **پایه‌ها** — شماره (مثل PB0) + لیبل Cube/شماتیک + نقش + HIGH یعنی چه
6. **پیش‌فرض امن** — بعد از `Init` خروجی‌ها چه وضعی دارند
7. **درخت اتصال** — این ماژول به کدام فایل‌ها وصل است (صدا می‌زند / صدا زده می‌شود)

اگر ماژول پایهٔ GPIO ندارد، در بخش پایه‌ها صریح بنویس: پایه ندارد.

قطبیت تا روی برد اندازه نشده «شماتیک» است، نه اندازه‌گیری‌شده.

ADC / PWM / UART / رله را در برگهٔ ماژول خاموش، Enable نکن مگر کاربر همان مرحله را خواسته باشد.
