# راهنمای اسکریپت‌های برنامه‌ریزی برد

این فایل توضیح هر اسکریپت این پوشه است: چه می‌کند، چرا این‌طور نوشته شده، و
دقیقاً چطور اجرا می‌شود. کد در سه فایل است:

| فایل | نقش |
|---|---|
| `stm32_cli.py` | لایهٔ مشترک: پیدا کردن ابزار، اجرای یک گام، ثابت‌های ناحیهٔ داده |
| `first_flash_changeover.py` | **اولین بار** — برد نو |
| `flash_changeover.py` | **همهٔ بارهای بعد** — با حفظ پارامترها و کالیبراسیون |

هیچ‌کدام کد برد نیستند؛ همه روی لپ‌تاپ اجرا می‌شوند.

---

## پیش‌نیاز مشترک

1. STM32CubeProgrammer نصب باشد.
2. `STM32_Programmer_CLI` یکی از این سه راه پیدا شود:
   - روی `PATH` باشد،
   - متغیر محیطی `STM32_PROGRAMMER_CLI` به مسیر کاملش اشاره کند،
   - یا با `--cli /مسیر/کامل/STM32_Programmer_CLI` داده شود.
3. ST-Link روی کانکتور **CON4** برد: `SWDIO`، `SWCLK`، `NRST`، `3.3V`، `GND`.

هر دو اسکریپت `--dry-run` دارند: دستورها را چاپ می‌کنند و **هیچ‌کاری روی برد
نمی‌کنند**. اولین اجرای هر اسکریپت روی یک برد همیشه با `--dry-run` باشد.

---

## ۱. `first_flash_changeover.py` — اولین بار

### چه زمانی
برد نو، یا بردی که هنوز هیچ‌وقت برنامه رویش نرفته. برای برد کالیبره‌شده
استفاده نکنید.

### چه می‌کند

| گام | کار | اگر مشکل باشد |
|---|---|---|
| ۱ | وصل می‌شود و نام قطعه را می‌خواند | اگر صریحاً خانوادهٔ دیگری (مثل F4) جواب بدهد، متوقف می‌شود |
| ۲ | ناحیهٔ داده را می‌خواند تا ببیند برد نو است یا نه | اگر داده داشته باشد **متوقف** می‌شود؛ اگر خوانده نشود (قفل) هم متوقف می‌شود |
| ۳ | پاک‌کردن کامل تراشه + نوشتن برنامه + بررسی | خطای ابزار، اجرا را متوقف می‌کند |
| ۴ | ناحیهٔ داده را دوباره می‌خواند و ثابت می‌کند پاک (0xFF) است | اگر پاک نبود، متوقف می‌شود |
| ۵ | ریست و نمایش وضعیت قفل | — |
| ۶ | قفل خواندن: **به‌صورت پیش‌فرض انجام نمی‌شود** | با `--lock` می‌شود، ولی برای برد نو توصیه نمی‌شود |

جملهٔ مهم: بعد از گام ۳، ناحیهٔ داده عمداً **پاک** می‌ماند. معنایش این است:
پارامترها روی پیش‌فرض‌های کامپایل می‌روند و جدول کالیبراسیون خاموش است، پس جریان
با خط gain/offset گزارش می‌شود. این همان «حالت کارخانه» صادقانه است.

### چرا روی برد کالیبره‌شده متوقف می‌شود
«اولین فلش» یعنی پاک‌کردن عمدی ناحیهٔ داده. اگر برد از قبل کالیبره شده باشد،
این کار کالیبراسیونش را بی‌صدا از بین می‌برد. پس اسکریپت قبل از دست‌زدن به فلش
می‌ایستد. برای برد کالیبره‌شده، اسکریپت دوم را استفاده کنید.

### اجرا

```bash
# ۱) دیدن دستورها
python3 Programmer/first_flash_changeover.py \
    --image build/ChangeOver.hex --label board7 --dry-run

# ۲) اجرای واقعی
python3 Programmer/first_flash_changeover.py \
    --image build/ChangeOver.hex --label board7

# ۳) اگر برد از قبل داده داشت و واقعاً می‌خواهید پاک شود
python3 Programmer/first_flash_changeover.py \
    --image build/ChangeOver.hex --label board7 --force-provisioned
```

گزینه‌ها:

| گزینه | کار |
|---|---|
| `--image` | فایل `.hex` یا `.bin` (اجباری) |
| `--label` | نام یا سریال برد؛ در نام فایل شاهد می‌آید |
| `--backup-dir` | پوشهٔ فایل‌های شاهد (پیش‌فرض `Programmer/backups`) |
| `--force-provisioned` | اجازهٔ اجرا روی بردی که از قبل داده دارد |
| `--lock` | روشن‌کردن قفل خواندن در پایان |
| `--dry-run` | فقط چاپ دستورها |
| `--cli` | مسیر کامل ابزار |

### دو فایل شاهد
- `probe_<label>_<date>.bin` — آنچه قبل از پاک‌شدن روی برد بود. اگر اسکریپت
  متوقف شود، این فایل نگه داشته می‌شود تا ببینید چه چیزی در خطر بوده است.
- `first_flash_<label>_<date>.bin` — ناحیهٔ داده بعد از نوشتن؛ اثبات اینکه حالت
  اولیه واقعاً پاک است.

### بعد از اجرا
اسکریپت خودش چک‌لیست را چاپ می‌کند: روشن‌کردن برد، دیدن خودآزمایی چراغ‌ها، باز
کردن پنل، کالیبراسیون از پنل، و بعد گرفتن اولین پشتیبان واقعی.

## ۲. `flash_changeover.py` — همهٔ بارهای بعد

### چه زمانی
هر بار که می‌خواهید برنامهٔ تازه روی بردی برود که پارامتر و کالیبراسیون دارد.

### چه می‌کند

| گام | کار |
|---|---|
| ۱ | پشتیبان ۸ کیلوبایت ناحیهٔ داده در یک فایل |
| ۲ | پاک‌کردن کامل تراشه + نوشتن برنامه + بررسی |
| ۳ | برگرداندن همان ۸ کیلوبایت + بررسی روی فلش |
| ۴ | ریست و نمایش وضعیت قفل |
| ۵ | قفل خواندن (اختیاری با `--lock`) |

### چرا این ترتیب
STM32F103 وقتی قفل خواندن دارد، با SWD فقط بعد از پاک‌کردن کامل برنامه می‌پذیرد.
آن پاک‌کردن کل فلش را می‌برد، از جمله:

| ناحیه | آدرس | اندازه |
|---|---|---|
| برنامه | `0x08000000` | ۵۶ کیلوبایت |
| بانک پارامترها | `0x0800E000` | ۴ کیلوبایت |
| جدول کالیبراسیون | `0x0800F000` | ۲ کیلوبایت |
| یدک | `0x0800F800` | ۲ کیلوبایت |

اسکریپت ۸ کیلوبایت داده را قبل از پاک‌کردن برمی‌دارد و بعد برمی‌گرداند.

### اجرا

```bash
# دیدن دستورها
python3 Programmer/flash_changeover.py --image build/ChangeOver.hex \
    --backup Programmer/backups/params_v1.90_board7.bin --dry-run

# فلش کردن با حفظ داده‌ها
python3 Programmer/flash_changeover.py --image build/ChangeOver.hex \
    --backup Programmer/backups/params_v1.90_board7.bin

# همان کار + قفل خواندن در پایان
python3 Programmer/flash_changeover.py --image build/ChangeOver.hex \
    --backup Programmer/backups/params_v1.90_board7.bin --lock

# فقط برگرداندن پشتیبان روی برد سالم
python3 Programmer/flash_changeover.py --restore-only \
    --backup Programmer/backups/params_v1.90_board7.bin
```

گزینه‌ها:

| گزینه | کار |
|---|---|
| `--image` | فایل `.hex` یا `.bin` (به‌جز حالت `--restore-only`) |
| `--backup` | فایل ناحیهٔ داده (اجباری) |
| `--restore-only` | فقط برگرداندن پشتیبان، بدون فلش |
| `--lock` | قفل خواندن در پایان |
| `--dry-run` | فقط چاپ دستورها |
| `--cli` | مسیر کامل ابزار |

### قواعد ایمنی داخل اسکریپت
- بدون پشتیبان سالم هیچ چیزی پاک نمی‌شود.
- پشتیبانی که اندازه‌اش ۸ کیلوبایت نباشد رد می‌شود.
- پشتیبانی که تمامش `0xFF` باشد رد می‌شود (یعنی برد خوانده نشده یا برد اشتباه است).
- پشتیبان بعد از برگشت با `-v` روی خود فلش بررسی می‌شود.
- هیچ خطایی «رد» نمی‌شود؛ هر خطا اجرا را متوقف می‌کند.

### خطر پشتیبان کهنه
اگر ساختار پارامترها یا جدول کالیبراسیون بین دو بیلد عوض شود، برگرداندن پشتیبان
قدیمی برنامه را با عدد بی‌معنی بالا می‌آورد و هیچ خطایی هم نمی‌دهد. پس نام
پشتیبان را با نسخهٔ بیلد بگذارید (مثل نمونه‌ها) و بعد از هر فلش، مقادیر
کالیبراسیون را یک بار در پنل ببینید.

---

## ۳. `stm32_cli.py` — لایهٔ مشترک

کارش سه چیز است و هیچ منطق بردی ندارد:
- پیدا کردن `STM32_Programmer_CLI` (سه راه بالا) و خطای روشن اگر پیدا نشد،
- اجرای یک گام با چاپ دستور و توقف صریح روی خطا،
- نگه‌داشتن دو عدد ثابت برد: شروع و اندازهٔ ناحیهٔ داده
  (`0x0800E000`، `0x2000`).

چرا جدا شده: هر دو اسکریپت یک سؤال را از یک ابزار می‌پرسند؛ کپی دومش همان
تکراری است که از هم جدا می‌افتد و بعد به کاربر دروغ می‌گوید.

---

## ۴. وضعیت آزمایش

| چه چیزی | چگونه آزمایش شد | نتیجه |
|---|---|---|
| ترتیب گام‌ها و پیام‌ها | `--dry-run` روی هر دو اسکریپت | درست |
| کل مسیر با برد نو | ابزار بدلی که ناحیهٔ داده را `0xFF` برمی‌گرداند | گام‌های ۱ تا ۶ اجرا و تمام شد |
| برد دارای داده | ابزار بدلی با دادهٔ تصادفی | پیش از فلش متوقف شد |
| برد قفل‌شده | ابزار بدلی که خواندن را رد می‌کند | متوقف شد، پیام قفل داد |
| پشتیبان کهنه | فایل ۱۰۰ بایتی | متوقف شد |
| پشتیبان تمام `0xFF` | فایل خالی | متوقف شد |
| فایل برنامهٔ ناموجود | `--image` اشتباه | پیش از اتصال به برد متوقف شد |

آزمایش‌نشده (باید روی برد واقعی انجام شود): خود دستورهای
`STM32_Programmer_CLI`، به‌خصوص مقدار `RDP=0xA5`. روی یک برد آزمایشی یک بار
اجرا کنید و با `-ob displ` ببینید سطح ۱ گزارش می‌شود.
