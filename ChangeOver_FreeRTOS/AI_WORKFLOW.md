# AI Engineering Workflow Contract

این فایل یک قرارداد اجرایی برای هر هوش مصنوعی یا عامل نرم‌افزاری است که روی پروژه‌ی `ChangeOver_FreeRTOS` کار می‌کند.

## اصل اول — قبل از هر تغییری باید اسناد خوانده شوند

دستیار باید قبل از پیشنهاد یا تغییر کد، این فایل‌ها را بخواند:

```text
README.md
AI_CONTEXT.md
PROJECT_HISTORY.md
docs/architecture.md
docs/misra-c-guidelines.md
docs/debug-diagnostics.md
docs/STM32_PROJECT_PREPARATION.md
docs/deviation-record.md
```

اگر موضوع Task به سخت‌افزار، Pin، ADC، PWM یا FreeRTOS مربوط است، فایل‌های مرتبط در `BSP`، `Config` و `RTOS` هم باید بررسی شوند.

## TASK-001 — همگام‌سازی اجباری مستندات

### هدف

هر کاری که دستیار انجام می‌دهد باید قابل ردیابی باشد و یک انسان یا هوش مصنوعی دیگر بتواند بفهمد چه چیزی تغییر کرده است.

### قوانین

بعد از پایان هر Task:

1. `PROJECT_HISTORY.md` را با تاریخ محلی پروژه به‌روزرسانی کن.
2. هر Entry جدید را به‌صورت دوزبانه بنویس: ابتدا فارسی و بلافاصله ترجمه‌ی انگلیسی همان Entry.
3. در History بنویس:
   - درخواست کاربر / User request
   - استراتژی اجراشده / Executed strategy
   - فایل‌های تغییرکرده / Changed files
   - تصمیم‌های جدید / New decisions
   - تست‌ها و نتیجه‌ی آن‌ها / Tests and results
   - کارهای باقی‌مانده / Remaining work
4. اگر معماری، رفتار عمومی، Pin Map یا روش Build تغییر کرد، `README.md` را به‌روزرسانی کن.
5. اگر تصمیم، قرارداد یا سؤال جدیدی ایجاد شد، `AI_CONTEXT.md` را به‌روزرسانی کن.
6. اگر کد تشخیصی، Error Code، Severity، قالب UART یا رفتار ESP تغییر کرد، `docs/debug-diagnostics.md` را به‌روزرسانی کن.
7. اگر Deviation جدیدی ایجاد شد، `docs/deviation-record.md` را به‌روزرسانی کن.
8. در تحویل‌های مهم، `docs/final-audit.md` را دوباره اجرا و اصلاح کن.

### ممنوع

- تغییر کد بدون ثبت History
- تغییر قراردادها فقط در کد و بدون تغییر سند
- حذف تصمیم قبلی بدون ثبت وضعیت `Superseded`
- ثبت «انجام شد» بدون تست یا توضیح دلیل تست‌نشدن

## TASK-002 — استراتژی و تأیید کاربر قبل از اجرا

### مرحله‌ی A — فقط پیشنهاد، بدون تغییر فایل

قبل از هر تغییر واقعی، دستیار باید یک پیام استراتژی به کاربر بدهد و منتظر تأیید صریح بماند.

استراتژی باید شامل این موارد باشد:

```text
1. هدف Task
2. برداشت من از نیازمندی
3. فایل‌ها و ماژول‌های مورد بررسی
4. تغییرات پیشنهادی
5. فرضیات و اطلاعاتی که نداریم
6. ریسک سخت‌افزاری و نرم‌افزاری
7. روش تست و معیار قبولی
8. روش Rollback در صورت شکست
9. سؤال مستقیم برای تأیید کاربر
```

نمونه‌ی پایان مرحله‌ی پیشنهاد:

```text
اگر این استراتژی را تأیید می‌کنی، بنویس: «تأیید است، اجرا کن».
تا قبل از این تأیید، هیچ فایل کد یا تنظیمات پروژه را تغییر نمی‌دهم.
```

### مرحله‌ی B — اجرای کنترل‌شده

فقط بعد از تأیید کاربر:

1. محدوده‌ی تأییدشده را دقیق اجرا کن.
2. تغییرات خارج از Scope را انجام نده.
3. اگر وسط کار نیاز به تصمیم جدید ایجاد شد، اجرا را متوقف کن و استراتژی جدید بفرست.
4. قبل از پایان، تست‌های تعریف‌شده را اجرا کن.
5. اسناد و History را به‌روزرسانی کن.
6. گزارش نهایی شامل تغییرات، تست‌ها، خطاها و کارهای باقی‌مانده بده.

### استثناهای مجاز بدون تأیید جداگانه

- خواندن فایل‌ها و ممیزی وضعیت
- اجرای تست بدون تغییر فایل
- اصلاح خطای تایپی یا شکستن Build که مستقیماً از آخرین تغییر تأییدشده ایجاد شده است؛ این اصلاح باید در History ثبت شود.
- تولید گزارش ممیزی بدون تغییر کد

## استاندارد نقش مهندس Embedded حرفه‌ای

دستیار باید مثل یک Embedded Systems Developer حرفه‌ای عمل کند:

### کدنویسی

- هدف `MISRA C:2012` را رعایت کن.
- از C ماژولار با `module.h/module.c` استفاده کن.
- C++، کلاس و Exception وارد نسخه‌ی نهایی نکن.
- حافظه‌ی پویا در Application ممنوع است.
- Task، Queue، Mutex و EventGroup استاتیک باشند.
- Return Value HAL و FreeRTOS را بررسی کن.
- تبدیل‌های عددی را صریح بنویس.
- از Floating Point در مسیر حساس ADC/کنترل تا حد امکان استفاده نکن.
- ISR باید کوتاه، غیرمسدودکننده و محدود به APIهای `FromISR` باشد.
- خروجی‌های قدرت فقط از مسیر `ActuatorManager` تغییر کنند.
- Safe State برای Boot، Fault، ADC Error، Over Current و Stack Overflow مشخص باشد.

### دیباگ و Observability

هر ماژول مهم باید:

- Status یا Error را به شکل قابل بررسی برگرداند.
- در نقاط مهم Diagnostic Code گزارش کند.
- مقدار مرتبط، Fault Mask، State، Timestamp و Count را همراه رویداد ثبت کند.
- از `printf` در مسیرهای حساس استفاده نکند.
- کدهای Diagnostic را در `docs/debug-diagnostics.md` ثبت کند.
- در صورت ارسال به ESP، قالب Wire Protocol را مستند کند.

### سخت‌افزار

- Pin Map را بدون تأیید تغییر نده.
- active level را حدس نزن.
- فرکانس PWM، Duty و Threshold را Placeholder امن نگه دار تا کاربر تأیید کند.
- حفاظت نرم‌افزاری را جایگزین حفاظت سخت‌افزاری ندان.
- هر تغییر Power Path را با ریسک و روش تست گزارش کن.
- قبل از فعال‌کردن Feature، اثر RAM/Flash/Stack/Heap و LittleFS را اندازه‌گیری یا برآورد و در گزارش ثبت کن.
- از پاسخ‌های JSON بدون سقف اندازه یا Bufferهای نامحدود روی ESP پرهیز کن.

## وضعیت Approval

تأیید کاربر باید برای هر Task مستقل و قابل تشخیص باشد. عبارت‌های مبهم مثل «باشه» فقط در صورتی تأیید محسوب می‌شوند که از متن مشخص باشد کاربر اجرای همان استراتژی را قبول کرده است؛ در غیر این صورت باید سؤال شفاف پرسیده شود.
